1. The Core Problem: You Can't Peek Inside

In a normal laptop, if you want to check whether a memory bit got corrupted, you just read the bit. In a quantum computer, reading a data qubit mid-calculation collapses its quantum state and erases the computation.

Instead, quantum error correction (QEC) spreads a small number of fragile logical qubits across many physical data qubits, surrounded by helper check qubits. We are only allowed to measure the check qubits. Each check tells us whether an odd number of its neighboring data qubits flipped — without revealing which one flipped.

2. Why Time Matters: 5 Rounds = 70 Detector Alarms

In a real quantum circuit, not only can data qubits flip — the check measurements themselves can lie (under SI1000 noise at p = 0.002, measurements fail with probability 5p = 1.0%!). To tell a real qubit flip apart from a glitchy measurement, the circuit repeats the checks for 5 rounds.

Instead of feeding raw check readings to the decoder, Stim computes detectors: Detector(t) = Check(t) XOR Check(t−1). A 1 simply means "something changed since the previous round." Across 5 rounds plus initialization and final readout, that gives exactly 70 detector bits (D0–D69) per shot.

4. Breaking Ties When BP Stalls: GF(2) OSD

Belief Propagation is fast, but on loopy qLDPC graphs two different error patterns can look equally likely, causing BP to oscillate without satisfying H · ê ≡ s (mod 2). When that happens, Ordered Statistics Decoding (OSD) takes BP's soft reliability scores, ranks the error mechanisms from least-reliable to most-reliable, and runs 128-bit packed binary Gaussian elimination (RREF) to guarantee a valid syndrome match.

5. Why Kaggle Shows 0.04483 While Local Shows 0.08129

Because this code protects 4 logical qubits per shot, getting 1 of the 4 wrong counts as 0.25 error on Kaggle (Per-Observable Bit MAE), whereas a strict shot-level check marks the entire shot as failed (1.00).

6. Engineering Constraints & Honest Trade-Offs

Getting this running reliably on an 8 GB RAM dual-core i3 laptop without touching banned packages required several practical engineering choices:

  • Bounded Memory (10k-Shot Chunking): Splitting the 100,000-shot basis arrays into 10,000-shot chunks with pre-allocated float32 per-thread workspaces eliminated RAM spikes.
  • Unclocked Import Warmup: Competition rules only time the two decode() calls, so Numba @njit compilation runs on dummy data during import decoder.
  • Known Runtime Headroom: On a 1.2 GHz dual-core laptop, 200k shots take ~50 s (above the 15.4 s judging target on 48 EPYC vCPUs + B200). Hard OSD-CS shots remain the main bottleneck.
  • Hyperparameters: Constants (ms_scale=0.78, damping=0.20, osd_w1=64, osd_w2=20) were tuned on sampled shots; see scripts/ablation_benchmark.py and tests/test_decoder.py in the repo.
